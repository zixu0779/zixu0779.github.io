<h4 id="1使用wave库"><a class="anchor" href="#1使用wave库">#</a> ①使用 Wave 库</h4>
<p>使用 python 的 Wave 库将左右声道加起来，导出为一个 a.wav 的文件</p>
<blockquote>
<p><strong>nchannels</strong>: 声道数，<strong>sampwidth</strong>: 量化位数，<strong>framerate</strong>: 采样频率，<strong>nframes</strong>: 采样点数</p>
</blockquote>
<p>Wave 写入对象</p>
<blockquote>
<p><strong>Wave_write.setnchannels(n)</strong><br />
 设置声道数。</p>
</blockquote>
<blockquote>
<p><strong>Wave_write.setsampwidth(n)</strong><br />
 设置采样字节长度为 n。</p>
</blockquote>
<blockquote>
<p><strong>Wave_write.setframerate(n)</strong><br />
 设置采样频率为 n。</p>
</blockquote>
<blockquote>
<p>Wave_write.writeframes(data)<br />
 写入音频帧并确保 nframes 是正确的。 如果输出流不可查找且在 data 被写入之后写入的总帧数与之前设定的 nframes 值不匹配将会引发错误。</p>
</blockquote>
<p>Write 读取对象</p>
<blockquote>
<p><strong>Wave_read.getnframes()</strong><br />
 返回音频总帧数。<br />
<strong>Wave_read.readframes(n)</strong><br />
 读取并返回以 bytes 对象表示的最多 n 帧音频。</p>
</blockquote>
<p>struct 库：将字节串解读为打包的二进制数据</p>
<blockquote>
<p><strong>struct.unpack(format, buffer)</strong><br />
 根据格式字符串 format 从缓冲区 buffer 解包（假定是由 pack (format, ...) 打包）。 结果为一个元组，即使其只包含一个条目。 缓冲区的字节大小必须匹配格式所要求的大小，如 calcsize () 所示。<br />
<strong>struct.pack(format, v1, v2, ...)</strong><br />
 返回一个 bytes 对象，其中包含根据格式字符串 format 打包的值 v1, v2, ... 参数个数必须与格式字符串所要求的值完全匹配。</p>
</blockquote>

<h3 id="dataleak129"><a class="anchor" href="#dataleak129">#</a> Dataleak（1.29）</h3>
<p><s>（隔了挺久的... 除了中间混了个 hgame，还有 HWS 入营赛 (虽然太菜了没啥用)，当然还有在认真地摸鱼啦）</s></p>
<p>连上远程，需要 leak 的数据长度为 22，<br />
IDA 查看 cJSON_PWN：<br />
<img loading="lazy" src="https://res.cloudinary.com/sycamore/image/upload/v1682436929/Typera/2023/04/4dcc2553fda4e522e344eccb3f71b8fd.png" alt="image-20230425233526169" /><br />
 内存结构还是比较清楚的<br />
按定义顺序，先是 buf，然后是 v5，最后是 v6 (存要 leak 的数据的地方)<br />
 两次循环，每次 buf、v5，写入数据长 14，结尾均有 \x00<br />
 每次 cJSON_Minify () 先处理 buf 的字符，然后读出 v5 中 11 字节</p>
<h4 id="漏洞点"><a class="anchor" href="#漏洞点">#</a> 漏洞点</h4>
<p>一共应该有两个漏洞点，可以从给的 so 文件中查看，</p>
<ul>
<li>处理 /* 的时候，会不断遍历中间的字符直到遇到 \x00 <s>（或 */ ）</s>，可能造成越界<br />
<img loading="lazy" src="https://res.cloudinary.com/sycamore/image/upload/v1682436937/Typera/2023/04/560f7380f89320b8d0bfa86942368be9.png" alt="image-20230425233533907" /></li>
<li>处理 &quot; 的时候，如果遇到 \ ，会越过两个字符<br />
<img loading="lazy" src="https://res.cloudinary.com/sycamore/image/upload/v1682436946/Typera/2023/04/0d185944b3f9a89c3f0cebb68e2e1cdd.png" alt="image-20230425233541340" /></li>
</ul>
<p>其中，第一个漏洞会将遍历到的字符舍去，所以后续的字符会填充到遍历过的字符位置上（包括 /*），而第二个漏洞只会越过 \ 后的两个字符，中间遍历的字符将会保留。</p>
<p>所以会有多个方法实现 data 的泄露，而第一个漏洞能够达成的效果强于第二个，所以可以全程使用第一个漏洞完成泄露</p>
<h4 id="漏洞利用"><a class="anchor" href="#漏洞利用">#</a> 漏洞利用</h4>
<p>由于一次只能读取 11 个字符，所以需要 leak 两次，<br />
但大致思路就是要利用漏洞，先越过 buf 后的 \x00，让 cJSON_PWN 能继续处理 v5 的字符，<br />
然后变换 /* 的位置，将 v5 内的字符替换为我们所需要的 data</p>
<h5 id="方法1"><a class="anchor" href="#方法1">#</a> 方法 1</h5>
<p>如果两个漏洞都想利用到的话，可以先使用第二个漏洞，将 \ 出现的位置放在 buf 的末尾（就是第 14 个字符），从而越过后面的 \x00 继续处理 v5，<br />
然后 /* 放在 v5 的开头，直接替换后面 16 个 data 的位置（算上开头的 /* 和末尾的 \x00 一共 16 个）<br />
<strong>exp1：</strong> <code>&quot;aaaaaaaaaaaa\/*aaaaaaaaaaaa</code> <br />
 获得前 11 个 data</p>
<p>要获得后 11 个 data，必须要把前 11 个 data 放到 buf 里面，才能让后 11 个 buf 出现在 v5 里被读出来，<br />
这里再用第二个漏洞实在是太麻烦了（仔细想了想，<strong>貌似也不可能</strong>），所以就用第一个解决。</p>
<p>一个的 /* 直接放在开头，把后面的 16 个字符换进来，另一个的 /* 放在第 6 个字符的位置，这样加上后面包括 \x00 在内的字符，一共有 11 个，<br />
这样就把前 11 个 data 再换到 buf 里面，这样后 11 个 data 就正好再 v5 里面被读取<br />
<strong> exp2：</strong> <code>/*aaaaaaaaaaaaaaaaa/*aaaaaaa</code> <br />
 获得后 11 个 data。（实际上<strong> exp2</strong> 前后两个可以颠倒，效果一致，因为这里的 exp 无论是先换 16 个字符还是先换那 11 个，都是一样的）</p>
<h5 id="方法2"><a class="anchor" href="#方法2">#</a> 方法 2</h5>
<p>方法 2 只变了 leak 前 11 个 data 的方法，后 11 个 data 的方式是一致的<br />
把 /* 放在 buf 的末尾，算上 \x00 一共会替换 4 个字符，为防止 data 的前 4 个字符被换进 buf，先用 aaaa 组成 v5 的前 4 个，然后再加上 /* ，替换出后面的 data<br />
<strong>exp：</strong> <code>aaaaaaaaaaaa/*aaaa/*aaaaaaaa</code></p>
