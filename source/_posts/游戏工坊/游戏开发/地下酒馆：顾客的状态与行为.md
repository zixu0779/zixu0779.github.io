在上一篇[《地下酒馆：模拟经营》](/游戏工坊/游戏开发/地下酒馆：模拟经营/)里，我简单介绍了《地下酒馆》的经营玩法。
本文着重说一下顾客 NPC 的状态和行为设计。这里用了一个有限状态机，把排队、点单、等餐等行为分成几个状态，再根据顾客到没到队首、菜有没有送到等条件切换状态。

## 顾客的状态流程

第一天开店后，除了剧情里会来的布兰，大厅里还会陆续来 6 批普通顾客。
（当然这是临时的设计，后续考虑根据声望等因素动态修改当天的顾客人数）

为了方便 Demo 的展示，前三批分别是结伴进店的顾客、一位热情的单人顾客和一位孤僻的单人顾客，后面几批再随机选类型。
这里按“批”来算，因为一批可能只有一人，也可能是几个人一起进来。

顾客当前的状态记在 `CustomerServicePoint.State` 里。进店前是 `Inactive`，顾客生成后进入 `Entering`，表示其加入菜单前的队伍。
顾客走到排队位置还不能进入下一个状态，队伍系统还要确认这位顾客是不是队首，只有顾客成为队首之后，才能进入 `Ordering`。

对于结伴进店的那组顾客，轮到其中一个顾客成为队首的时候，队伍系统会根据他的 `PartyId` 找到同组的顾客，再给每个人分配菜单前的点单位置。
然后组员会从队列里散开，在菜单前各找一个位置，且等所有人都站好才进入 `Ordering`。

![轮到这组顾客点单后，四位组员离开队列、转向菜单，在各自的位置站好](https://res.cloudinary.com/sycamore/image/upload/v1795154314/Typora/2026/10/25/dungeon-tavern-customer-party-menu-positions-turn.gif)

---
普通顾客选完菜后会自动记录订单，并通过头顶气泡展示菜品，然后离开排队的队伍，进入 `FindingSeat` 状态。
以第一天的老铁匠布兰为例，他有一份预设的饮品订单。他在菜单前停留片刻，登记订单后先进入 `ShowingOrder`，短暂展示点好的饮品，随后才去找座位。

这个状态虽然名字叫“找座位”，但对于当前 Demo 的临时逻辑，座位早在进店前就已经留好了。
而这一步实际上是直接获取已有的座位，再进入下一个 `MovingToSeat` 状态，导航到目标座位。
之所以这样设计一个状态，主要是为了给后续扩展作准备，即假如出现位置不够的情况。

顾客走到桌边，还要转向桌面并执行入座动作才会进入等餐状态。
之后可以在等餐和进食状态之间来回切换，等整份订单吃完，才会喊老板来结账。
离店时也是一样，开始往外走是 `Leaving`，真正到达门口以后才进入 `Finished`。

![顾客从进店到离店的状态变化，包含等餐、布兰点单和提前打烊的分支](https://res.cloudinary.com/sycamore/image/upload/v1795154300/Typora/2026/10/25/dungeon-tavern-customer-states-zh.png)

每一帧，`Update()` 会把 `arrived` 初始设为 `false`。如果顾客正在进店、排队、前往座位或离店，就检查他有没有走到目标位置。
随后调用 `Tick(Time.deltaTime, arrived)`。
`Tick()` 按状态检查不同的条件。例如，等餐时要看订单里有没有已经送到、还没吃完的餐品：

```csharp
case CustomerOrderState.WaitingForFood:
    if (Order.HasFood) ChangeState(CustomerOrderState.Eating);
    else if (Order.AllConsumed) ChangeState(CustomerOrderState.AwaitingSettlement);
    break;
```

`ChangeState()` 会更新状态和头顶气泡，通知订阅了状态变化的对象。
对于需要停留一会儿的状态，比如展示订单，也在这里设置倒计时。

玩家送餐和结账则由 `Interact()` 处理。比如老板送到了顾客还在等的菜，就会清空手里拿的东西，让顾客进入进食状态。

## 顾客的座位分配

大厅里有长桌、小圆桌和大圆桌。下面按我调整后的设计说明选座和拼桌规则，Demo 中的代码还保留着前一版实现。
顾客进店前，`SeatRegistry` 会先预留这次进店所需的位置。因此，即使椅子上还没有人坐，也可能是另一位正在点单的顾客的位置。

![游戏中的三种桌子模型，从左至右为长桌、小圆桌和大圆桌](https://res.cloudinary.com/sycamore/image/upload/v1795154302/Typora/2026/10/25/dungeon-tavern-customer-table-models.png)

### 独自进店的顾客

单人顾客有孤僻和热情两种。两者都会先找整张空着的长桌，再找空的小圆桌。如果都没有空位，就看已有顾客的长桌上还能不能拼座。
二者的区别在于选哪一张凳子：

- **孤僻的顾客**会优先找同侧紧邻的座位和正对面的座位都空着的位置。找不到，再考虑长桌上其他空位。
- **热情的顾客**对相邻座位没有这层要求。只要长桌还有空位，哪张凳子都可以。所以按逻辑也会坐到孤僻顾客的旁边。

长桌没有可拼的位置时，单人前来的顾客才会考虑一张完全空着的大圆桌。最后实在没有座位了，就会站在大厅里的某个位置进行等待。

代码里给每个可用位置算一个优先级，数值越小越靠前。
遍历时只在找到**更高**优先级的位置时才替换原来的选择，因此同一档优先级如果有好几张凳子时，取的是先检查到的那一张。

```csharp
int rank = Rank(candidate, customer.SeatingKind);
if (rank < best) { best = rank; seat = candidate; }
```

### 结伴进店的顾客

结伴顾客每组 2 至 4 人，优先选择空的大圆桌。即使大厅里有三张空凳子，只要分散在不同桌旁，也不会接待同一组三个人。只有三个空位在同一个桌子上时，才会纳入考虑。

`TryReserveParty()` 会先找出一张空的大圆桌，确认有效座位数够用，再给组内每个人分配一张凳子。
如果分配到一半失败，已经给这组人留的座位会一起释放。整组都分到座位之后，才算作分配完成。
如果两个人占用一张四人桌，另外两个空位只会分给小于2人的新顾客；
且只有等到最后一位组员起身释放座位，这张圆桌中被结伴顾客占用的座位才重新算作空闲。

## 多人点单

同一组顾客进店时会拿到相同的 `PartyId`。
当其中一人到达队首后，队列会用这个编号找到其余组员，让他们在菜单前围成浅弧。
轮到这一组时，后面排队的人会继续等待。
等组员各自点完、共享菜品也商量好了，整组才一起离开菜单。

每个人会从个人菜品中选一到两份，再选一杯饮品。
选个人菜的时候，每个人都有各自的计时，所以几个人站在一起，头顶出现的气泡内容也不完全同步。
气泡下面是正在考虑的菜，确认后图标移到上面，下面就能继续展示下一道。

![气泡上层是已经确认的菜品，下层带勾的是正在确认的菜品](https://res.cloudinary.com/sycamore/image/upload/v1795154312/Typora/2026/10/25/dungeon-tavern-customer-order-bubble.png)

组里还可以合点共享菜品，目前的菜单中有铁锅洞菇炖肉和炭烤穴猪拼盘。
以拼盘为例，当一名顾客提议时，他头顶会出现拼盘的图标和问号。
其他组员手上如果还有一道菜正在确认，会先把它选完，再各自表态。
只要有人给出叉号，这道菜就不加入订单；其余组员全部同意，才把拼盘加进每个人头顶的已确认菜品里。

![四位顾客在菜单前各自选菜，再用头顶的气泡提议和确认共享菜](https://res.cloudinary.com/sycamore/image/upload/v1795154304/Typora/2026/10/25/dungeon-tavern-customer-group-order.gif)

在一轮投票结束时，`votes` 收齐了除提议者外所有组员的答复。
是否把这道菜保留下来，只需通过下面这个代码：

```csharp
if (votes.Values.All(yes => yes)) shared.Add(item);
```

虽然每个人头顶的气泡都包含了这个拼盘，但厨房只需要送一份。
实现时，是单独建一张共享订单，并把其中的共享菜关联到每位组员的订单上。
计算送达时，则按这份菜去重，只要送到其中一人的手里，其他人的订单也能看到已经送达。

另外，共享菜的进食时间和价钱则只由第一位组员计算一次，避免四个人吃一份拼盘却收四份钱。

## 送餐、结账与打烊

目前 Demo 里普通顾客的菜品都使用装满的酒杯代替。送到桌边时，会逐一匹配这位顾客还没收到的个人餐品和共享菜。
比如一位顾客还缺一杯饮品和一份共享拼盘，送去的第一杯会记作他的饮品。
之后把另一杯送给个人餐品已经上齐的任意组员，就能交付拼盘。

一位顾客点了两份餐，送来第一份就可以开始吃。
吃完时第二份还没上，他会从 `Eating` 回到 `WaitingForFood`；如果老板在他吃完前已经送来第二份，他就继续吃。等个人餐品和自己参与的共享菜都送达、吃完，头顶气泡才会变成“结账”。

顾客各自在座位上付账。普通顾客结清就会起身离开，布兰的结账操作则会先触发桌边对话，等剧情交回控制，再完成结算。

玩家也可以在顾客吃完之前拉下拉杆，临时关店。
这时会暂停后续顾客入场，取消在店顾客未结清的订单，让他们离开，未付的钱不会算进收入。
还没进店的顾客仍保留在当天的安排里，重新营业后可以接着来。
等当天的顾客都已离店且布兰的剧情结束，伊芙才会提醒老板正式打烊。
